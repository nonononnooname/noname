## БЛОК 1. ФУНДАМЕНТАЛЬНАЯ КОНЦЕПЦИЯ

### 1.1. Проблема: почему существующие блокчейны уязвимы к квантовой угрозе

Каждый крупный блокчейн (Bitcoin, Ethereum, Solana, BNB Chain) ставит свою безопасность на криптографию эллиптических кривых — **secp256k1** для транзакций и **BLS** для валидаторов (Ethereum). Достаточно мощный квантовый компьютер (CRQC — cryptographically relevant quantum computer) ломает обе эти системы через алгоритм Шора.

Три вектора угрозы:

1. **Harvest now, decrypt later (укради сейчас, расшифруй потом).** Злоумышленники уже сегодня архивируют публичные данные блокчейна и подписи, ожидая появления CRQC. Всё, что подписано через ECDSA или зашифровано через X25519 сегодня — на таймере. Блокчейн особенно уязвим: данные публичны и неизменяемы, а каждый раскрытый при трате публичный ключ хранится вечно.

2. **BLS-валидаторы хрупки.** Агрегированные BLS-кворумы (Ethereum) коллапсируют в момент, когда pairing-based допущения перестают работать. У цепочки, чья финализация зависит от BLS-агрегации, нет плавного сценария отказа.

3. **Миграция ≠ патч.** Прикрутить постквантовую криптографию к существующим secp256k1-цепочкам ломает адресные схемы, финализацию и десятилетие инструментария. Постквантовая защита должна быть заложена в сеть с genesis-блока.

**Контекст угрозы (выверенная формулировка)** 【C6】【C7】:

- **Оценки сроков CRQC.** Консервативные оценки NIST и академического сообщества помещают появление CRQC в горизонт **10–20 лет**, при оптимистичных оценках — **5–10 лет**; единого консенсуса нет. (Источник по формулировке — whitepaper Tidecoin, §2.1.)
- **Регуляторный дедлайн (NIST).** **NIST IR 8547** рекомендует мигрировать на постквантовую криптографию **к 2030 году**, с обязательным выводом уязвимых алгоритмов из эксплуатации **после 2030 и полным запретом после 2035**.
- **Снижение оценки ресурсов атаки (Google Quantum AI).** В работе Крейга Гидни (Google Quantum AI), препринт **май 2025** («How to factor 2048 bit RSA integers with less than a million noisy qubits», arXiv:2505.15917), оценка числа кубитов для взлома RSA-2048 снижена с **~20 млн (оценка Гидни–Экерő 2019)** до **<1 млн** — это ~20× (≈95%) сокращение **относительно оценки 2019 года**, достигнутое за счёт алгоритмических и архитектурных улучшений, а не за один год.
- **Стандарты NIST.** **13 августа 2024 года** NIST финализировал три постквантовых стандарта: **FIPS 203 (ML-KEM), FIPS 204 (ML-DSA), FIPS 205 (SLH-DSA)** — по итогам ~8-летнего отбора (2016–2024). На отбор было подано 82 заявки, из которых 69 были приняты как «полные и корректные» к Round 1. **Четвёртый алгоритм — FN-DSA (на базе Falcon) — на момент составления документа всё ещё в статусе черновика (FIPS 206), не финализирован** 【C3】.

| | **ATQM (Atom Quantum)** | **Areth** |

**Логика аббревиатуры A.T.Q.M. (технически корректная версия)** 【C1】【C2】:

- **A** = Atom. Корневой бренд экосистемы ATOM Group.
- **T** = Technology. NIST-стандартизированные постквантовые примитивы (FIPS 203/204; FN-DSA/Falcon — черновик FIPS 206).
- **Q** = Quantum. Архитектура, рассчитанная на сохранение безопасности в постквантовую эпоху.

Если маркетинг хочет сохранить нумерологический якорь «17», он живёт **только** в retail-каналах Фила и не появляется в техническом spec.

## БЛОК 2. ТЕХНИЧЕСКАЯ АРХИТЕКТУРА ARETH

### 2.1. Происхождение: форк Reth, а не «с нуля»

Areth — это **fork-descendant** проекта Reth (высокопроизводительный Ethereum-клиент на Rust). Сохранено зрелое хранилище, EVM, дерево состояний; заменены все места, где живут криптографические допущения Ethereum.

> **Терминологическая точность** 【C8】: формулировка «построено с нуля / from genesis» к самому **клиенту** неприменима — Areth наследует кодовую базу Reth (это явно заявлено в документе Areth: «Areth is a fork-descendant of Reth»). Корректно говорить: **PQ-стек заложен с genesis-блока сети**, при этом исполнение/хранилище — зрелый форк Reth.

**Что сохранено из Reth:**

| Компонент | Функция |
|---|---|
| MDBX storage provider | Высокопроизводительное хранилище состояний |
| Merkle-Patricia trie | Дерево состояний для верификации |
| REVM execution engine | Движок исполнения смарт-контрактов |
| Transaction pool & fetcher | Пул транзакций и их получение |
| Payload builder | Построение блоков |
| Snap-style state sync | Быстрая синхронизация состояния |
| Node runtime & RPC server | Среда выполнения ноды и API-сервер |

**Что заменено на постквантовые эквиваленты:**

| Ethereum (старое) | Areth (новое) | Причина замены |
|---|---|---|
| Gasper (консенсус) | HotStuff | Детерминистическая финализация вместо вероятностной |
| devp2p (транспорт) | PQ session | Квантово-уязвимый обмен ключами |
| ECDSA (подпись tx) | ML-DSA / FN-DSA | secp256k1 ломается алгоритмом Шора |
| ENR (идентификация нод) | ArethNodeId | Привязка к PQ-ключам |
| X25519 (обмен ключами) | ML-KEM-768 | Curve25519 уязвима |
| `eth_*` (RPC namespace) | `areth_*` | Новая поверхность API |
| Probabilistic finality | Block-bound finality | Детерминистическая финализация |

*Таблицы «сохранено/заменено» сверены с документом Areth (§3) — совпадают полностью.*

### 2.2. Архитектура сети: три роли, один транспорт

Каждая нода говорит на одном зашифрованном транспорте (ключ выводится через ML-KEM); различается только «груз»:

1. **Discovery.** ANR-записи и поиск пиров. Без состояния валидаторов и данных исполнения.
2. **Public Execution.** Синхронизация финализированных блоков, gossip транзакций, snap-style распределение состояния.
3. **Validator.** HotStuff-предложения, голоса, QC (Quorum Certificates), коммиты и сертификаты финализации.

**Транспортный уровень:**

```
ML-KEM-768  +  AES-GCM  +  ML-DSA transcript binding
```

- **ML-KEM-768** — выводит сессионный ключ.
- **AES-GCM** — AEAD с защитой от replay-атак и epoch rekeying.
- **ML-DSA** — подписывает транскрипт хендшейка, защищая от downgrade-атак.

> Примечание (информационное): Areth использует ML-KEM-**768** (NIST Category 3) для транспорта. Для сравнения, Tidecoin (whitepaper, §8.1) использует ML-KEM-**512** (Category 1) — Areth выбрал более высокий уровень безопасности транспорта. Это проектное решение, не ошибка.

### 2.4. Консенсус: HotStuff, подписанный ML-DSA

**2-chain Jolteon-style HotStuff** — линейный BFT-протокол с детерминистической финализацией:

```
PROPOSAL → QC → COMMIT-VOTE → COMMIT CERT → FINALITY
```

| Параметр | Значение |
|---|---|
| Кворум | `⌊2/3⌋ + 1` ML-DSA подписей |
| Начальный таймаут раунда | 1.0 секунда |
| Ожидание payload | ~750 мс |
| Максимальный backoff pacemaker | 30 с (только при реальном стопе сети) |
| Тип финализации | Block-bound, детерминистическая |
| **Откаты после финализации** | **0 (post-finality property)** 【C4】 |

**Отличие от Ethereum:** в Ethereum финализация вероятностная (Casper FFG финализирует через 2 эпохи = 64 слота ≈ 12,8 мин). В Areth блок финализирован в момент получения commit certificate. Нет BLS и нет агрегации.

> **Уточнение по форкам** 【C4】: «0 откатов» — это свойство HotStuff **после** финализации. До получения commit certificate pre-finality форки возможны — это базовое свойство **любого** BFT-протокола, а не дефект. Корректная формулировка: «**reorgs после финализации = 0**; до финализации форки возможны, финализация наступает в течение <1 с в текущей тестовой топологии». Документ Areth сам формулирует это аккуратно: «Reorgs once finalized: 0» и «Reorgs after finality: 0».

> **Технический caveat по отказу от агрегации** 【C12】: «no BLS, no aggregation» подаётся только как плюс, но имеет цену. Без агрегации каждый голос валидатора — это отдельная ML-DSA-подпись (для ML-DSA-65 ≈ **3 309 байт**, по данным whitepaper Tidecoin §4.2.5). Quorum/commit certificate с N валидаторами несёт ~N × 3,3 КБ подписей, тогда как агрегированный BLS — один агрегат ~96 байт. На production-масштабе (50+ валидаторов) это значимая нагрузка на полосу и хранилище. Это честный инженерный trade-off, который должен быть назван явно.

### 2.5. Постквантовые примитивы: полный стек

| Уровень | Примитив | Примечание |
|---|---|---|
| Аутентификация транзакций | ML-DSA / FN-DSA | Один ключ или threshold-of-N |
| Подписи консенсуса | ML-DSA | Без BLS, без агрегации (см. caveat 2.4) |
| Обмен ключами транспорта | ML-KEM-768 | Все соединения нода-нода |
| AEAD транспорта | AES-GCM | Replay protection + epoch rekeying |
| Идентификация ноды | ML-DSA node key + ML-KEM transport key | Связаны в `ArethNodeId` |

**Дефолтные алгоритмы и статус стандартизации (выверено)** 【C3】:

- **ML-DSA-65** — основная схема подписи. **Финализированный стандарт NIST: FIPS 204 (13.08.2024).** Ранее — CRYSTALS-Dilithium.
- **FN-DSA-512** — для компактных подписей (меньший размер). **Внимание: FN-DSA (на базе Falcon) — это будущий FIPS 206, который на сегодня в статусе черновика (Initial Public Draft, ~сентябрь 2025), финал ожидается в конце 2026 – начале 2027.** Это **не** финализированный стандарт.
- **ML-KEM-768** — для всего обмена ключами. **Финализированный стандарт NIST: FIPS 203 (13.08.2024).** Ранее — CRYSTALS-Kyber. ML-KEM-512 и ML-KEM-1024 также доступны в `areth-crypto`.

> **Следствие для маркетинга** 【C3】: формулировка «NIST-standardized, top to bottom» / «всё на NIST-стандартах» **корректна для ML-KEM и ML-DSA, но не для FN-DSA**. Точная формулировка: «ML-KEM и ML-DSA — финализированные стандарты NIST (FIPS 203/204); FN-DSA — на финальной стадии стандартизации (черновик FIPS 206)».

**Threshold-аккаунты — first-class:** многоустройственная авторизация (threshold-of-N) работает нативно, без сложных смарт-контрактов.

### 2.6. Модель транзакций

- **EVM-совместимость:** Nonce, chain id, gas, EIP-1559, access lists, EIP-2718 envelopes, RLP — всё то же. Solidity-тулинг переносится.
- **PQ-derived sender:** адреса вычисляются из `keccak(domain || prefixed_key)[12..]`, не через secp256k1 recovery. По-прежнему 20 байт, EVM-native.
- **Threshold accounts:** threshold-of-N — нативный режим авторизации.
- **Нет blob-транзакций:** blob/KZG отклоняются на границе пула.

*Сверено с документом Areth (§8) — совпадает.*

> **Технический контекст по размерам подписей (добавлено для честности trade-off)** 【C12】: PQ-подписи существенно больше ECDSA. По данным whitepaper Tidecoin (§4.1.6, §4.2.5): ECDSA-подпись — 64 байта; FN-DSA-512 (Falcon-512) — подпись ~666 байт (padded) + публичный ключ 897 байт; ML-DSA-65 — подпись 3 309 байт + публичный ключ 1 952 байта. Именно поэтому `areth-txpool` отдельно «оптимизирован под размеры PQ-подписей». EVM-совместимость на уровне контрактов сохраняется, но экономика транзакций (calldata/полоса/хранилище) меняется — это надо учитывать при бенчмарках, а не замалчивать.

### 2.7. Производительность

**Текущий результат:** детерминистическая финализация **< 1 секунды в текущей тестовой топологии** 【C9】.

| Метрика | Значение |
|---|---|
| Блоков финализировано end-to-end (smoke runs) | 300+ |
| Топология тестов | 4 валидатора + full-client |
| Вероятностных подтверждений для ожидания | 0 |

> **Честная квалификация результата** 【C9】: smoke-тест на **4 валидаторах** — это **сигнал корректности кода (code-correctness signal), а не production-бенчмарк**. Документ Areth сам формулирует это аккуратно: «300+ blocks finalized end-to-end in smoke runs», «4 validators + full-client topology, verified», «< 1 s — deterministic finality on a healthy network». Поведение на production-масштабе (50+ валидаторов, реальная география, ML-DSA-кворумы без агрегации — см. 2.4) — предмет дальнейшего тестирования. Эта честность **не ослабляет** питч: профессионалы и так понимают, что 4-валидаторская топология ≠ production.

**Честное сравнение:** round timeout ≠ block interval. Финализация зависит от реального времени: payload build → proposal → vote quorum → QC → commit-vote quorum → persistence. Pacemaker уходит к 30 с **только** при реальном стопе сети.

### 2.8. Торговый движок (Trading Stack) — статус: ROADMAP / R&D 【C5】

> **Перенесено из «архитектуры» в «дорожную карту».** Документ Areth размещает торговый стек в разделе **«Roadmap — on-chain trading»** (§11) и в roadmap-сводке (§16). Раздел «Capabilities — what ships today» (§10) **CLOB не содержит**. Поэтому подавать CLOB на одном уровне с базовым L1 как «готовую часть архитектуры» — неточно.

**Концепция (целевое направление):** от постквантового L1 к on-chain Hyperliquid.

| Слой | Реализация (целевая) | Основа |
|---|---|---|
| Matching engine | Native precompile, price-time-priority CLOB | `areth-revm` |
| Order transactions | EIP-2718 envelope, PQ-signed end-to-end | `ARETH_TX_ORDER_PQ_TYPE` |
| Markets | Perps, spot, dated futures; validator-signed oracle | HotStuff quorum |
| Risk engine | Cross/isolated margin, ADL, insurance fund | `areth-storage` |
| Settlement | В том же финализированном блоке, что и матч | Block-bound finality |

> **Реалистичная оценка** 【C5】: децентрализованный CLOB с матчингом и финализацией <1 с — серьёзная R&D-задача. Hyperliquid достигает скорости за счёт **централизованного** секвенсора; повторить это в децентрализованной HotStuff-сети — инженерный moonshot уровня «может занять 18+ месяцев, может не получиться». Текущий статус: **design phase, post-mainnet**. Компонент **не блокирует** запуск L1 и торговых dApp в стандартном EVM-формате.

### 2.9. Постквантовые кошельки

| Платформа | Реализация |

### 【C6】 Блок 1.1 — «Google обозначил дедлайн: к 2029 году»

- **Обоснование:** Google не публиковал «дедлайн 2029». Это упрощение/искажение позиции. Заменено на защитимые, ссылающиеся на первоисточники формулировки, сохраняющие urgency.

### 【C7】 Блок 1.1 — «За последний год число кубитов сократилось на 95% (исследование 2024)»

- **Было:** «За последний год количество необходимых кубитов для взлома текущей криптографии сократилось на 95% (исследование 2024).»
- **Стало:** «В работе Гидни (Google Quantum AI), **май 2025**, оценка кубитов для RSA-2048 снижена с ~20 млн (2019) до <1 млн — ~20× (≈95%) **относительно оценки 2019 года**, за счёт алгоритмических/архитектурных улучшений».
- **Источник:** Craig Gidney, «How to factor 2048 bit RSA integers with less than a million noisy qubits», arXiv:2505.15917 (препринт май 2025; v опубликован июль 2025): *«…20 million noisy qubits [2019]… less than a million noisy qubits [2025].»* Это сравнение 2019↔2025, не «за год».
- **Обоснование:** Две неточности: (1) дата — 2025, не 2024; (2) «за последний год» неверно — сокращение получено относительно оценки 2019 года (6-летний горизонт). Цифра ~95% корректна, но её надо атрибутировать правильно, иначе DD ловит небрежность.

### 【C8】 Удалённый Блок 7 — ложные утверждения о конкурентах и «единственности»

- **Было (ключевые строки):**
  - «ATQM is the only decentralized Layer 1 built from genesis on CRYSTALS».
  - «Microsoft, Apple, IBM — haven't even started developing a defense».
- **Стало:** Блок 7 удалён; эти утверждения исключены из любых публичных материалов как **фактически ложные** (и создающие defamation / false-advertising риск).
- **Источник (опровержения):**
  - *«Единственный L1 с genesis на CRYSTALS»* — опровергается **в пределах самого корпуса**: whitepaper Tidecoin, Abstract/§1: *«The network has been in continuous operation since December 27, 2020»*, *«every single transaction secured by post-quantum signatures»* — то есть PQ-блокчейн с genesis существует с 2020 года (использует Falcon/ML-DSA). Кроме того, документ Areth (§2): *«Areth is a fork-descendant of Reth»* — т.е. Areth **не** «from genesis» как клиент, а форк. И «CRYSTALS» неточно: ML-DSA = CRYSTALS-Dilithium, но FN-DSA/Falcon — **не** CRYSTALS (NTRU-семейство).
  - *«IBM не начал разрабатывать защиту»* — обратно реальности: IBM **со-изобрёл** ML-KEM (Kyber), ML-DSA (Dilithium) и FN-DSA (Falcon) — те самые алгоритмы, на которых построен Areth. Первоисточник: IBM Newsroom, 13.08.2024 — *«ML-KEM (originally CRYSTALS-Kyber) and ML-DSA (originally CRYSTALS-Dilithium) were developed by IBM researchers… a fourth IBM-developed algorithm, FN-DSA (originally FALCON)…».*
  - *«Apple не начал»* — Apple развернул **PQ3** (на базе ML-KEM/Kyber) в iMessage с iOS 17.4 (2024). Первоисточник: Apple Security (security.apple.com/blog/imessage-pq3) — выбран Kyber/ML-KEM.
  - *«Microsoft не начал»* — Microsoft имеет публичную PQC-реализацию (SymCrypt с ML-KEM/ML-DSA).
- **Обоснование:** Утверждения ложны и проверяемы за минуты. «IBM не начал» особенно абсурдно — IBM является автором алгоритмов, лежащих в основе Areth. Помимо репутационного провала, это база для исков от названных компаний. Питч и так силён без ложных сравнений.

## II. ИНЖЕНЕРНЫЕ КВАЛИФИКАЦИИ (важно для DD)

### 【C9】 Блоки 2.7, 9 — performance как production-бенчмарк

- **Было:** «Финализация < 1 секунды (детерминистическая, на здоровой сети)» подавалась как готовая характеристика; 4 валидатора без оговорки.
- **Стало:** «<1 с **в текущей тестовой топологии (4 валидатора)**; это code-correctness signal, не production-бенчмарк; поведение на 50+ валидаторах — предстоит».
- **Источник (документ Areth, дословно):** §9 — *«300+ blocks finalized end-to-end in smoke runs»*, *«4 validators + full-client topology, verified»*, *«< 1 s — deterministic finality on a healthy network»*. Areth честно говорит «smoke runs».
- **Обоснование:** 4-валидаторская smoke-топология ≠ production. Честная квалификация не ослабляет питч и снимает очевидный DD-вопрос. Связано с C12 (без агрегации размер кворума растёт с N).

### 【C12】 Блоки 2.4, 2.6 — размеры PQ-подписей и цена отказа от агрегации (добавлено)

- **Было:** отсутствовало; «no BLS, no aggregation» и «тот же EVM» подавались только как плюсы.
- **Стало:** добавлены honest trade-off-примечания о размерах подписей и о стоимости кворума без агрегации.
- **Источник (whitepaper Tidecoin, дословно, §4.2.5 / §4.1.6, таблицы):** ML-DSA-65: Signature **3,309 bytes**, Public Key **1,952 bytes**; Falcon-512: Signature (padded) **666 bytes**, PK **897 bytes**; для сравнения ECDSA-подпись — 64 байта (Tidecoin §2.3: *«666 bytes for Falcon-512 vs. 64 bytes for ECDSA»*).
- **Обоснование:** PQ-подписи в ~10–50× больше ECDSA. Без агрегации каждый голос валидатора = отдельная ML-DSA-подпись (~3,3 КБ), поэтому commit certificate растёт линейно с числом валидаторов — в отличие от единственного ~96-байтного BLS-агрегата. Это реальная нагрузка на полосу/хранилище на масштабе; `areth-txpool` не зря «оптимизирован под размеры PQ-подписей». Технически честный документ обязан это назвать.

## VI. ОТКРЫТЫЙ ВОПРОС К CEO (без изменений по сути ревью)

Главная развилка: приоритетная аудитория — **институциональная** или **retail**. Текущая (исходная) конфигурация пыталась обслуживать обе одновременно (двойная токеномика + нумерология + воронка) — самая опасная: любая утечка обнажает дуальность. Выбор одной стратегии снижает риск. Техническая часть (после правок C1–C14) одинаково пригодна для обеих аудиторий, потому что стала **фактически верной**.

## VII. О НУМЕРОЛОГИИ «17» (если supply остаётся 17B)

QAnon-эстетика — это **узор** (17 / 0.17 / 0.0017 / 170,000 / 17/170/1700/17,000), а не одна цифра. Если «17B» сохраняется как маркетинговый якорь, остальные параметры (цена, burn %, validator stake, размеры паков) должны **перестать быть кратными 17**, чтобы разорвать паттерн. В техническом spec нумерология отсутствует полностью (см. C2). Рекомендация ревью — перейти на 10B (стандарт TON/Sui) — снимает вопрос целиком.
